要解决的问题

资料分散，结论查不到出处

论文摘录、实验记录、组会纪要散落在不同文件里。搜到一句话却无法回答「这句话来自哪份资料的第几段」，两周后就无法回查。

任务与资料断链

行动项记在待办里、依据记在笔记里。任务完成后想说明「当时依据是什么」，只能重新翻文件。

周报靠人工再拼一遍

本周做了什么、还欠什么、下周做什么，全都要从纪要和待办里手动整理，条目还常常丢掉出处。

核心功能

  1. 1

    导入资料并保留出处

    粘贴或选择 Markdown / TXT，按 500 字符窗口、60 字符重叠分块。出处三元组是「文件名 · 第 N 块 · 版本 R」。资料名与分块序号进入数据库，回看时能取到原文。

  2. 2

    带出处的真实检索

    输入一句自然语言问题，中文按二元切分生成检索词交给数据库，由 MATCH(content) AGAINST(?) 在 seekdb 内完成过滤与相关度排序。页面只显示数据库返回的原文片段与出处，不生成任何没有出处的结论。

  3. 3

    从出处新建行动项

    任一条命中结果都能作为出处创建任务：标题、负责人、截止日期、状态。行动项记住分块标识与当时的版本号，同一幂等键重复提交返回同一条记录。

  4. 4

    生成可复制周报

    按「本周完成 / 待解决问题 / 下周计划」三段整理，条目自带出处与逾期标记，纯文本可一键复制。周报按模板规则生成并在正文注明，不冒充 AI 生成内容。

界面为中文主界面，包含空态提示（还没有资料 / 没有符合条件的行动项）、失败提示与重试入口 （后端不可用时明确说明「不会用示例结果替代真实检索」），并在窄屏下重排为单列布局。

技术架构

React 前端（中文工作台）

Vite + React 19 + Tailwind 4。四个标签页：资料检索 / 资料库 / 行动项 / 周报，另有「关于本站」说明实现与验收步骤。只调用一组同源 /api/* 接口。

↓ HTTP JSON

Node 核心服务

server/index.ts 把 node:http 请求转成 Web Request，交给与浏览器端共用的一份业务核心 functions/core/：分块、检索词生成、输入校验、版本策略、周报规则、HTTP 路由。服务本身不缓存任何业务数据。

↓ seekdb npm SDK（MySQL 协议）

seekdb 1.4.0 · 唯一承担业务数据的数据库

三张表：researchloop.rl_sources（资料与当前版本）、researchloop.rl_material_chunks（分块正文 + FULLTEXT INDEX … WITH PARSER ngram + revision + retired_at）、researchloop.rl_actions（行动项与出处引用，含 ref_chunk_revision）。 检索、过滤、排序全部在数据库内完成，进程内不做内存集合检索。

关键实现

检索下推进数据库

默认解析器对中文返回空结果，实测改用 ngram 全文索引（索引词长 2）后数据库能直接给出相关度分数。检索语句只有一条：

SELECT id, source_name, chunk_no, content,
       MATCH(content) AGAINST(?) AS score
FROM researchloop.rl_material_chunks
WHERE workspace_id = ? AND retired_at IS NULL
  AND MATCH(content) AGAINST(?)
ORDER BY score DESC LIMIT ?

资料版本与出处稳定性

同名资料再次导入且内容变化时：版本号 +1，新分块写入，被替换的旧分块打上 retired_at 退休并保留在库中（不批量删除）。检索与列表只看当前版本；已有引用凭原始分块标识仍能解析，周报出处标注锁定的版本号。

内容长度超出分块容量上限时直接返回 material_too_large 并说明需要多少块，不静默丢弃尾部。

幂等写入与空间隔离

分块标识为 SHA-256(工作空间 | 资料名 | 块号 | 内容)，重复导入相同内容只更新不新增；行动项标识由调用方幂等键派生，网络结果未知时重试不会产生第二条。所有读写都以 workspace_id 为条件，公开示例空间与个人空间互不可见。

周报为模板规则，出处可回溯

三段内容由任务状态、完成日期与截止日期推导，响应带 rule: "template" 标记，正文首行写明整理方式。每条条目带「出处：文件名 · 第 N 块 · 版本 R」，逾期条目额外标注。

真实验证结果

验收脚本 server/verify-flow.ts 通过真实 HTTP 请求驱动核心服务与 seekdb，逐项断言并写出证据文件 researchloop/results/seekdb-verify.json。运行环境：Windows + WSL 内 seekdb 1.4.0（127.0.0.1:2881）， Node 22.20 运行核心服务（127.0.0.1:8788）。最近一次运行 30 项断言全部通过。

本地运行步骤

核心应用完全在本机运行，发布环境不需要、也不会连接云端 seekdb。以下步骤按 Windows + WSL 实测编写。

  1. 1. 启动 seekdb（WSL，127.0.0.1:2881）

    # 一次性安装：官方镜像下载 → 校验 SHA-256 → 解包，不注册系统服务、不删除任何目录
wsl -d Ubuntu -- bash /mnt/e/project/oceanbase-ecosystem-2026/stepfun/scripts/install-seekdb-wsl.sh

# 启动（保持前台运行，数据目录位于 WSL 原生文件系统）
wsl -d Ubuntu -- bash /mnt/e/project/oceanbase-ecosystem-2026/stepfun/scripts/start-seekdb-wsl.sh

    确认端口可达：Windows 侧 netstat -ano | findstr 2881 出现 LISTENING。

  2. 2. 启动核心服务（真实数据库读写）

    cd qoder/researchloop/server
npm ci
npm start          # 监听 http://127.0.0.1:8788，首次启动自动建表并补齐版本列

    冒烟检查：curl http://127.0.0.1:8788/api/health 返回 "backend":"seekdb"。

  3. 3. 启动前端工作台

    cd qoder/researchloop
npm ci
npm run dev        # Vite 输出 http://127.0.0.1:5173，/api 代理到 8788

    浏览器打开该地址 →「资料库」→「导入 5 份公开示例资料」→「资料检索」问「怎样保证实验可以复现」。

  4. 4. 复跑端到端验收

    cd qoder/researchloop
npm run verify     # 真实 HTTP + 真实 seekdb，逐项断言并写 results/seekdb-verify.json

    期望末行输出「全部通过：30/30」。

  5. 5. 本地预览本介绍页（可选）

    cd qoder/researchloop
npm run serve:site # http://127.0.0.1:4174 提供静态介绍页与截图

生产构建：npm run build（先 tsc --noEmit 类型检查，再产出 dist/）。端口约定：seekdb 2881、核心服务 8788、前端 5173、介绍页 4174。

边界与说明

  • 周报由模板规则生成，页面与文本都明确标注，不声称由 AI 生成。
  • 检索只返回数据库中真实存在且带出处的片段；后端不可用时页面显示失败状态，不用内存示例结果替代。
  • 公开示例资料为参赛者整理的虚构学习科研材料，不含真实个人数据、凭据或未公开实验结果。
  • 本页是 Qoder Sites 静态作品展示站（作品介绍与验收入口）；赛题指定的数据库能力由本机 seekdb 真实实现，不使用其他数据库冒充指定技术。
  • 退休分块只标记不删除，因此历史出处可解析；导入与验证会在数据库中累积记录，不做批量清理。
  • 资料长度上限 200,000 字符 / 单份最多 460 块；超出即明确拒绝，不静默截断。
